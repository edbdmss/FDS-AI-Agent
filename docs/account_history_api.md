# 계좌 이력 자동 추론 API

`POST /v1/transactions/score`에 아래 형식으로 거래를 전달한다. 클라이언트는 거래마다 새로운 UUID를 만들고 재시도할 때는 같은 UUID와 같은 내용을 전달한다.

```json
{
  "transaction_id": "7c2e9ce0-cad8-4efe-9af9-8eb75e385305",
  "step": 355,
  "type": "TRANSFER",
  "amount": 500,
  "oldbalanceOrg": 500,
  "oldbalanceDest": 0,
  "nameOrig": "demo_sender_1",
  "nameDest": "demo_receiver_1"
}
```

DB에 저장된 송금자·수취인 거래 중 `step < 현재 step`인 이력만 집계한다. 과거 건수·금액 합계·평균·활동 step 수·마지막 거래 이후 간격을 계산하고 저장 모델에 전달한다. 이력이 없으면 학습 규칙에 따라 건수·금액은 0, 간격은 -1로 처리한다.

같은 ID와 같은 내용으로 재요청하면 `replayed: true`와 저장된 예측을 반환한다. 내용이 다르면 HTTP 409를 반환한다. 해당 계좌에 이미 더 큰 step의 거래가 있으면 역순 입력을 거부한다. 두 계좌를 정렬한 순서로 잠그고 계산·저장을 하나의 DB 트랜잭션에서 수행한다. 거래를 발생 step 순서대로 전송해야 하며 누락된 과거 거래를 자동 복원하지 않는다.

`sql/002_account_history.sql`에서 계좌 컬럼·원본 요청·조회 인덱스를 추가한다. 기존 계좌 ID 없는 저장 행은 이력에 포함하지 않는다. 원본 PaySim 이력은 아직 Supabase에 업로드하지 않았으므로 새 계좌의 첫 요청은 DB 기준 신규 이력으로 평가한다. 과거 데이터가 모두 존재하는 오프라인 Test와 입력 이력 범위가 다름을 명시한다.

Supabase 연동 확인에서 이전 step 집계, 동일 step 제외, 동일 ID 재요청, 내용 충돌, 역순 입력 거부를 확인한다. 검증용으로 생성한 행만 삭제한다.

API는 로컬 시연용으로 사용한다. 공개 배포 전 인증·사용자별 데이터 접근 제한을 추가한다. 기존 `/v1/predict-and-save`는 계좌 이력 자동 연결이나 재시도 중복 방지를 제공하지 않으므로 신규 거래 수집은 이 문서의 API를 사용한다.
